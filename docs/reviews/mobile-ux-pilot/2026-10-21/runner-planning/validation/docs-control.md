It supplies no separate regression-only scope collection or relationship for a phone safety check that must not claim to cover F-01's original `proxy-mouse` scope. This is a documentation/schema-expression limitation, not an observed claim about what the helper accepts or rejects.

The source is explicit about those relationships: `affects` contains the original scope objects; `fix.required_check_ids` and `verification_ids` link checks; a check's `covers` and `scope_results` use finding/scope IDs. The contract says to claim only the level reached and never describe expected behavior as observed; see frozen [evidence-contract.md, Verification](../before/skills/mobile-web-ux-runner/references/evidence-contract.md#verification).

For the phone checks, setting `covers: [{finding_id: "F-01", scope_id: "proxy-mouse"}]` would make an unsupported coverage assertion: iPhone/Safari keyboard/focus safety in portrait or landscape is not the recorded Linux mouse reproduction condition. Adding phone scopes to `F-01.affects` to satisfy that link would change the original scope. Inventing new fields or undocumented scope IDs would also fail the question's constraints.

An unscoped candidate would keep the two phone checks' `covers: []` and link them only through `fix.required_check_ids`, with their regression purpose in the documented scenario/expected/conditions text. This avoids a false desktop-coverage link. However, the old documentation does **not specify that this is an admissible complete applied-fix plan**, how independently named phone regression portions would participate in scope-level results, or whether such checks satisfy its complete-remaining-coverage gate. Therefore I would present this as a truthful partial/narrative representation and the precise unresolved documentation point, not assert that it is a complete schema-supported plan or a validated ledger. A literal empty `covers` list being representable in JSON does not establish the intended schema semantics.

The phone build being unprovisioned is a separate execution gap. Its declared record is not a phone-reachable handoff, and blank results do not become evidence through a build declaration. The old reporting instructions require a fix check to name a phone-reachable build containing the fix and tell the operator to retain the missing build as an open question. See frozen [reporting.md, Outputs and Device-entry selection](../before/skills/mobile-web-ux-runner/references/reporting.md#outputs). The two build IDs should remain distinct; the documentation does not justify silently replacing `fix.build_id: buildB-local` with `buildB-phone` or transferring a local pass to the planned build.

If a person later reports a clear portrait-only pass, preserve that result only for `C-phone-portrait`, with the actual supplied device, build, setup, conditions, behavior and evidence. Keep `C-phone-landscape` `not_run`, with blank actual/evidence. Do not combine two independent outcomes into a whole-phone pass. If one entry had explicitly contained both orientations, its overall result would be partial, but the old `scope_results` linkage cannot truthfully use `proxy-mouse` to name the independent phone portions; the two-entry form avoids discarding the clear portrait observation. The old results procedure expressly requires preserving portrait passes while landscape remains unrun; see frozen [reporting.md, Results-only procedure](../before/skills/mobile-web-ux-runner/references/reporting.md#results-only-procedure).

A portrait pass does **not verify F-01**. It exercises a different browser/device/input scenario, landscape is still unrun, the phone build and setup must be confirmed independently, and relevant unknown wiring still limits dependent claims. The original local intermittent observation and `proxy-mouse` scope remain intact and unresolved; F-01 stays implemented unless actual eligible evidence supports another status. Phone keyboard/focus results may describe their own reported behavior, but cannot refute the original desktop failure. For an intermittent contrary-evidence conclusion, bare passes are insufficient: the old contract requires a pass count and an evidence-based causal explanation excluding the mechanism, as well as matching relevant conditions. No such facts are supplied here.

The two independently reportable human checks consume **two reserved entries**. With budget 6, the applied-device-dependent-fix reserve is `floor(6 / 2) = 3`: this plan uses 2 of those 3 slots and 2 of the 6 total script slots. One reserved slot and four total script slots remain unused, assuming there are no other applied device-dependent fixes. Count both entries even though one fix motivates them; do not merge portrait and landscape to lower the count. A later portrait pass preserves that original two-entry admission/history while the remaining script contains only the still-unrun landscape entry. The old documentation's `application_basis` preserves original admission without allowing missing or failed results to rewrite the original plan. See frozen [reporting.md, Device-entry selection](../before/skills/mobile-web-ux-runner/references/reporting.md#device-entry-selection) and [ledger-schema.md, Top-level records](../before/skills/mobile-web-ux-runner/references/ledger-schema.md#top-level-records).

The old documentation's wording does not give a separate machine field for target intent, so a complete answer must disclose that ambiguity rather than treat `level: target` as an observation.
