Its inspected public contracts do not establish a response that satisfies `swiss-transit-episode/1`, or the source identity required by the existing natal-anchor contract. This is a documented-contract gap, not proof that its private implementation cannot supply those capabilities.

The recommended next step is a bounded AstroWay engineering/provenance request, specified below. If the provider cannot supply that contract or editable implementation access, design an owned adapter separately. The owned `patternlike-app` calculator is a substantial starting point, but neither its current API nor its existing cycle solver is a drop-in replacement.

This is a new discovery record. The original [source discovery](source-discovery.md), [qualification checklist](source-qualification.md), evaluation reports, and candidate artifacts remain unchanged. No implementation, configuration, activation, publication, or deployment was performed; both candidates remain inactive under the existing release decision. No person was contacted, no secret was read or exported, and no calculation request or real birth data was sent.

## Natal-source compatibility is an earlier gate

`swiss.server.ts` only retains an explicitly returned, valid `data.positionSource`. The required identity is:

```text
engine       = swiss-ephemeris
engineVersion= exact qualified identifier
dataId       = exact qualified file-set identifier
frame        = tropical-apparent-geocentric-true-equinox-of-date
timeScale    = UT
returnedFlags= 258
```

If the actual `/chart` response lacks that object, ordinary service-backed natal charts can still be usable, but `assessTransitAnchors` returns `unqualified_source`; a compliant episode endpoint alone would not enable the feature. **The public schema establishes no promise of this object; its actual runtime absence was not tested.** All three natal samples must match, and episode resolution compares every source field against all three anchor sources. [Swiss client](../../../src/lib/astro/swiss.server.ts), [anchor validator](../../../src/lib/astro/transit-anchors.ts), [episode source comparison](../../../src/lib/astro/transit-episodes.ts).

Consequently, an owned solver cannot merely label itself AstroWay-compatible because both use Swiss. It needs attested matching engine/data/frame/flags and numerical qualification, or an explicitly designed migration that generates natal chart/anchor evidence and episodes from the owned source. That migration must preserve Placidus house/angle provenance and handle snapshots/cache versions; existing anchors must not be relabeled.

This is local source/data evidence, not deployed binary evidence.

Concrete redesign remains necessary:

- `/v1/cycles` emits normalized envelopes and rounded passes, discarding the required bracket/station/leg/window proof (`src/cycles.ts:1296`). It does not return the episode wire shape or six-field position source.
- Time-only root/station refinement at two/one seconds does not establish the application's angular/speed residual limits (`:549`, `:348`).
- Existing closure uses a distance beyond the orb plus a retrograde-arc allowance, and an envelope can span out-of-orb gaps. The application instead proves closure with adjacent station-connected legs and retains distinct windows (`:1167`).
- Existing cycles include station-on-target tangencies, omit quincunx, use different orb policies, and can scan farther than the application's ±1,460-day bound (`src/cycles.ts:670`, `src/cycle-policy.ts:196`).
- The declared container digest can be derived from version labels; it does not attest ephemeris files. Any reuse must preserve the service's license/source-offer materials and explicit non-Placidus fallback marker (`src/engine.ts:52`, `:549`).

These are reasons to reuse selected primitives under a new design and qualification, not to adapt the existing cycle JSON mechanically. No calculator code, policy, dependency, data file or deployment was changed or executed for this review.
